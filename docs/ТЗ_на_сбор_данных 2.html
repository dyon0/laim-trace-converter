1. Введение

В рамках проекта по созданию системы распознавания аномалий в мультиагентных системах (МАС) необходимо организовать сбор, нормализацию и валидацию телеметрических данных, поступающих от AI-агентов. Источником данных служит платформа AEF Tracing, реализующая сбор трассировок агентов в формате, расширяющем открытый стандарт OpenTelemetry (OTel). Собранные OTel-трейсы содержат спаны с дополнительными атрибутами aef.*, которые описывают семантику операций, характерных для LLM-агентов (вызовы LLM, использование инструментов, графовые переходы и т.п.).

Система распознавания аномалий, в свою очередь, оперирует последовательностями векторов признаков (Execution Performance Indicators – EPI, и семантические эмбеддинги LLM-ответов – SEM), извлекаемых из данных выполнения агентов. Каждый агент и его действия представлены отдельными событиями, упорядоченными во времени.

Для обучения детекторов аномалий необходимо:

  1. Получить «нормальные» (т.е. отражающие максимально мощное подмножество легитимных сценариев выполнения) трассы выполнения МАС, на которых будет проводиться обучение и настройка системы.
  2. Обеспечить извлечение всех атрибутов, необходимых для вычисления признаков EPI- и SEM- векторов, а также структурных метаданных (отношения "родитель-потомок" между спанами в исходных деревьях трассировок).
  3. Иметь возможность восстановить древовидную структуру каждого трейса для будущего применения графовых нейросетей (pLSTM, GNN).

Данный документ определяет формат, правила и процедуры загрузки и валидации данных на этапе их поступления из хранилищ AEF.

2. Общие требования к данным

Все поступающие данные должны удовлетворять следующим ключевым требованиям:

  1. Корректность – типы данных, форматы и диапазоны значений должны строго соответствовать описанной в разделе 3 спецификации. Любое отклонение (например, нарушение base64-кодирования идентификаторов, NULL-значения, невалидные JSON-строки, отрицательное время etc) недопустимо.
  2. Консистентность – значения атрибутов должны быть согласованы между собой и с логикой OTel/AEF. Например, для HTTP-спанов обязаны присутствовать непустые заголовки, а для не-LLM спанов все LLM-метрики должны быть замещены стражевыми значениями (-1, -1.0, False etc).
  3. Полнота – каждый обязательный атрибут спецификации должен присутствовать в записи и не принимать значение NULL (см. раздел 7).
  4. Репрезентативность – обучающая выборка нормальных трасс должна покрывать все (максимально возможные вариативные) разрешённые сценарии поведения реальных агентов, и не содержать аномалий. Рекомендуется каждый легитимный сценарий выполнения МАС представлять несколькими разнообразными трассировками выполнений агентов. Рекомендуемый объем данных (на текущем этапе разработки системы) – порядка 10^5 - 10^6 трассировок на каждую конкретную МАС.
  5. Соответствие спецификации – загружаемые данные должны проходить автоматизированную валидацию по правилам, зафиксированным в данной спецификации; трассировки, содержащие несоответствующие записи будут отбраковываны.

4. Схема загружаемых данных

Описанная выше спецификация автоматически транслируется в схему Polars и набор валидационных правил, которые используются при загрузке Parquet-файлов. Ключевые особенности схемы:

  • Все строковые поля, идентифицирующие спаны (trace_id, span_id, parent_span_id, agent_id), объявлены как pl.String.
  • Перечисления (status_code, aef_kind, otel_kind, http_method) реализованы через pl.Enum с фиксированным набором допустимых значений.
  • Числовые поля имеют явно заданные типы: pl.Int64 или pl.Float32.
  • Булевы поля – pl.Boolean.

При чтении Parquet-файла используется объект pl.Schema, сформированный динамически из таблицы спецификации. Код генерации схемы приведён в Приложении A.

7. Стражевые значения и отказ от NULL

Важным решением архитектуры данных является полный запрет NULL в пользу страж-значений (sentinel values). Это продиктовано следующими соображениями:

  • NULL не имеет однозначной семантики. Он может означать «не применимо», «значение неизвестно», «данные утеряны при передаче» или «ошибка источника». Такая неоднозначность делает невозможным автоматический анализ и обучение моделей.
  • Страж-значения явно кодируют состояние «не применимо». Например, llm_prompt_tokens = -1 для спана, не являющегося вызовом LLM, немедленно и безошибочно говорит аналитику (или алгоритму), что этот атрибут не имеет смысла для данного объекта.
  • Устойчивость к ошибкам сбора. Если источник должен был предоставить какое-то значение, но не предоставил, то на этапе загрузки это будет выявлено (нарушится NOT NULL). В результате некорректные данные отбраковываются немедленно, и не порождают скрытые проблемы на следующих этапах.
  • Упрощение инженерии признаков. При построении EPI-векторов агрегирующие функции могут просто игнорировать спаны со страж-значениями, вместо того чтобы обрабатывать каждый NULL отдельно (по нескольким контекстам: неприменимость атрибута, возможная потеря данных etc).

Каждый страж описан в спецификации: для числовых полей, где допустимы только неотрицательные значения в норме, используется -1 (или -1.0); для булевых – false (пересечение доменов стражей и булевых атрибутов в данном случае допустимо в силу семантики последних; в будущем это решение может быть пересмотрено); для строк – "" (пустая строка) или специальные константы ("NONE", "root", "outside").

Благодаря этому конвейер данных получается полностью детерминированным: любое поле всегда содержит значение, и это значение всегда интерпретируется однозначно.

8. Разбор групп атрибутов

Ниже кратко пояснена роль каждой группы атрибутов в контексте задач анализа данных и обучения системы распознавания аномалий.

Идентификаторы (trace_id, span_id, parent_span_id, agent_id)
Обеспечивают восстановление полной иерархии спанов. agent_id позволяет сгруппировать все спаны, относящиеся к одному агенту, и вычислить EPI-векторы. parent_span_id даёт возможность агрегировать данные, определить глубину и количество дочерних спанов.
Время (start_time_ns, end_time_ns)
Необходимо для хронологического упорядочивания спанов при построении последовательностей EPI и SEM векторов, а также для расчёта длительностей и временных интервалов.
Статус (status_code, status_message)
Позволяет выявлять явные ошибки (например, таймауты инструментов) и отличать их от нормального выполнения. При агрегации EPI это даёт признаки tool_failures, error_count и т.п.
Классификация (aef_kind, otel_kind, span_name)
Основные дискриминаторы семантики операции. По ним фильтруются LLM-вызовы для построения SEM векторов, считаются уникальные инструменты, определяется энтропия последовательности действий агента etc.
Текстовые данные (input_text, output_text)
Из output_text LLM-спанов извлекаются эмбеддинги для семантической последовательности (для неLLM-спанов в экспериментальном режиме также извлекается семантика на основе структурированного текста технического лога). input_text агентов содержит полный контекст задачи, используемый при вычислении complexity_score.
LLM-атрибуты (llm_model, llm_prompt_tokens, …)
Предоставляют детальные метрики каждого вызова модели. Агрегируются в EPI-признаки: суммарные токены, средние значения, параметры генерации. Изменение параметров (например, аномально высокая температура) может служить индикатором атаки.
HTTP и Kafka (http_method, …, kafka_bootstrap_servers)
Позволяют отслеживать взаимодействие с внешними сервисами: точки входа (путь, метод), коды ответов, заголовки, топики Kafka. При анализе аномалий могут выявляться необычные паттерны сетевых запросов.
Метаданные LangGraph (meta_langgraph_step, …)
Содержат информацию о графе выполнения: номер шага, имя узла, триггеры, маршрут. Эти признаки крайне полезны для обнаружения отклонений в потоке управления (например, пропуск обязательного узла).
Служебные (session_id, service_name, service_version)
Идентифицируют сессию пользователя и версию сервиса, что важно для воспроизводимости и фильтрации данных при дообучении.
